## 1. Общие сведения

### 1.1. Цель проекта
Создать полнофункциональную альтернативу коммерческого приложения **Table Filter, Charts & Spreadsheets for Confluence** (Stiltsoft), покрывающую все его ключевые макросы и сценарии использования, и довести её до состояния **полностью установленного и принятого приложения** на рабочем инстансе Confluence DC (сборка → установка через UPM → приёмочные испытания).

### 1.2. Границы проекта
- **Внутри scope:** все макросы-аналоги (см. раздел 7), REST API, хранение пользовательских данных, админ-конфигурация, i18n (ru/en), документация пользователя и администратора, сборка и процедура установки, приёмочные тесты.
- **Вне scope:** публикация в Atlassian Marketplace (и связанная с ней лицензионная инфраструктура Marketplace License API), версия для Confluence Cloud (Forge/Connect), интеграции помимо перечисленных в разделе 7.9.

### 1.3. Результаты анализа рынка (GitHub-ресёрч)
Поиск готовых open-source альтернатив проведён 2026-10-26 по GitHub (API search: `confluence table filter`, `confluence plugin`, `confluence macro charts`, `confluence plugin spreadsheet` и др.).

**Вывод: готового полного open-source аналога не существует.** Найденное:

| Репозиторий | Суть | Пригодность |
|---|---|---|
| `1Corporation/ConfluenceFilterPlugin` | «Confluence plugin with filters for tables» | 0 звёзд, заброшен, прототипного уровня — не пригоден |
| `grager/castconfluencetableplus` | JS-скрипты фильтрации таблиц Confluence | 0 звёзд, концепт — только как идея |
| `reisi007/openapi-confluence-converter` | Генерация сортируемых таблиц из OpenAPI | Не профильная |
| Коллекции user-macro (различные) | jQuery-фильтры таблиц как user macro | Работают, но нет конфигуратора, профилей, экспорта, диаграмм — покрывают ~5 % функциональности |

Коммерческие альтернативы для ориентира: Aura Table (MOSAIC), Smart Tables (Creativas), Advanced Tables (Bob Swift/Appfire). Все платные и закрытые.

**Архитектурное решение:** не портировать закрытый код, а собрать аналог на проверенных **open-source кирпичах** (см. раздел 6) внутри собственного P2-приложения. Это даёт лицензионную чистоту (Apache-2.0/MIT) и полный контроль.

## 4. Высокоуровневая архитектура

### 4.1. Состав P2-приложения (один jar)

```
OpenTFC (P2 app)
├── macros/          — 8 макросов (раздел 7), каждый: xhtml-модуль + velocity-параметры + soy/JS-конфигуратор
├── webresources/    — WRM-контексты: display (view page), editor (macro browser), configurator
├── rest/            — REST v1 (/rest/opentfc/1.0): источники данных, профили, экспорт, состояние
├── servlet/         — экспорт файлов (CSV/XLSX/PNG), download-эндпоинты
├── ao/              — AO-таблицы: FilterProfile, SpreadsheetMeta, UserSettings
├── services/        — TableExtractor (парсинг storage format → модель таблиц),
│                      DataSourceResolver (CSV/JSON/XLSX/вложение/URL/Jira),
│                      SqlEngine (DuckDB), ChartConfig, SpreadsheetStore
├── cluster/         — кэш-инвалидация через cluster event (Hazelcast topic)
└── admin/           — страница админ-конфигурации (лимиты, whitelist URL, права)
```

### 4.2. Поток данных (display-режим)
1. Рендер страницы: макрос рендерит «сырую» таблицу (или отдаёт контейнер + конфиг JSON).
2. На клиенте JS-движок подтягивает конфиг, при необходимости — данные источников через REST (`GET /rest/opentfc/1.0/source/{pageId}/{macroId}`).
3. Табличный движок (AG Grid) строит интерактивную таблицу: фильтры, сортировка, totals, пагинация.
4. Диаграммы/пивот читают ту же табличную модель (в т.ч. из соседних макросов в цепочке через атрибут `source-macro-id`).

### 4.3. Цепочки макросов (ключевая фича прототипа)
Поддержка композиции `Source → Table Transformer → Pivot Table → Chart from Table → Table Filter`:
- каждый макрос имеет стабильный `macroId` (UUID) в параметрах;
-下游-макрос ссылается на источник через `source-macro-id` либо обёрткой (body-вложение) — поддерживаются **оба** способа как в прототипе;
- рендер вложенных макросов: backend-режим «dry-render» исходного макроса → извлечение таблицы (см. 5.2).

### 4.4. Хранение данных
| Данные | Где хранится | Обоснование |
|---|---|---|
| Конфигурация макросов | storage format страницы (параметры макроса) | переживает экспорт/импорт, кластерно безопасно |
| Профили фильтров | AO `FilterProfile` (pageId, macroId, userKey, name, JSON) | per-user данные |
| Таблицы-спредшиты | вложение страницы (сериализованный XLSX-совместимый файл) | версионность, бэкапы, экспорт пространства «из коробки», кластерная безопасность |
| Пользовательские настройки UI | AO `UserSettings` + localStorage | — |

**Запрет** на локальные файловые кэши без инвалидации; серверный кэш распарсенных источников — только через `atlassian-cache` с TTL и сбросом cluster-событием при изменении вложения.

## 5. Ключевые технические механизмы

### 5.1. Рендеринг и «обёртывание» произвольных таблиц
- Body-макросы (Table Filter, Chart from Table, Pivot Table, Table Transformer) принимают в теле: нативную таблицу Confluence, другой макрос с таблицей (Jira Issues, Page Properties Report, Task Report, Content by Label, Include page и др.), CSV/JSON-макросы-источники.
- Извлечение таблиц из произвольного контента: рендер тела макроса в XHTML (`RenderingService`/`ViewMarkupService`) → парсинг (`XmlEventReaderFactory`) → сбор модели: заголовки, строки, типы колонок (автоопределение: text/number/date/currency/percent/link/user/jira-status).

### 5.2. Источники данных из файлов
- CSV/TSV: вложение текущей/чужой страницы или URL (whitelist в админке). Кодировки: UTF-8/UTF-16/cp1251 (автодетект + ручной выбор). Разделитель `,`/`;`/tab — автодетект.
- JSON: массив объектов или массив массивов; JSONPath для выбора узла.
- XLSX: лист + диапазон (A1 notation), парсинг Apache POI.
- Периодическое обновление по расписанию (мин. интервал — админский лимит) с кэш-инвалидацией на кластере.

### 5.3. SQL-движок (Table Transformer)
- **DuckDB JDBC (MIT)** в in-memory режиме: временные таблицы из source tables, полный SQL: `SELECT, WHERE, GROUP BY, ORDER BY, LIMIT, JOIN (INNER/LEFT/RIGHT/FULL/CROSS), UNION [ALL], PIVOT/UNPIVOT, оконные функции`, скалярные функции (строковые, даты, CASE, COALESCE и т.д.).
- Имена таблиц: `T1`, `T2`, … по порядку источников (совместимо с синтаксисом прототипа `SELECT * FROM T1`).
- Sandboxing: только SELECT/DML-чтение (read-only соединение), лимит времени запроса (админ-лимит, по умолчанию 10 с), лимит размера результата, отсутствие файлового и сетевого I/O (отключённые extensions), защита от SQL-инъекций неактуальна (запрос редактирует автор страницы, но логирование и лимиты обязательны).
- Расширенный диалект прототипа: функции `T1.'Column Name'` с кавычками и пробелами в идентификаторах, `::date`-касты, `CASE WHEN` — проверить совместимость с DuckDB-синтаксисом, недостающее покрыть препроцессором запроса.

### 5.4. Кластерная безопасность (DC)
- Отсутствие singleton-состояния в памяти ноды без синхронизации.
- AO-таблицы — общие через БД.
- Кэш распарсенных CSV/JSON — `atlassian-cache` (кластерный), инвалидация через cluster event `source.updated`.
- Спредшиты — через вложения (общие), конкурентное редактирование: блокировка редактирования на время сессии + merge при сохранении по версии (см. 7.6).

## 8. Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| NFR-01 | Производительность | Страница с Table Filter на таблице 5 000 строк × 20 колонок: первый интерактив ≤ 1,5 с после DOMContentLoaded (виртуализация строк обязательна); UI-поток не блокируется > 50 мс |
| NFR-02 | Производительность | SQL Transformer: запрос по 100 000 строк суммарно ≤ 5 с; таблица-результат ≤ 50 000 ячеек (иначе пагинация) |
| NFR-03 | Производительность | Спредшит 100×100 с формулами открывается ≤ 2 с; пересчёт формул ≤ 500 мс на правку |
| NFR-04 | Кластер | Нет локально-авторитетных данных: AO + вложения + кластерный кэш; cluster event инвалидация источников; отсутствие сессий-в-памяти (всё в БД/вложениях) |
| NFR-05 | Безопасность | Полное экранирование пользовательского содержимого (XSS): имена файлов, значения ячеек, URL; CSP-совместимость; никаких inline `eval` |
| NFR-06 | Безопасность | Все изменяющие REST-эндпоинты с XSRF-токеном (`AtlassianTokenFilter`); проверка прав: просмотр страницы-источника и скачивание вложения — на сервере, не на клиенте |
| NFR-07 | Безопасность | URL-источники только из админ-whitelist (SSRF-защита: запрет internal IP/localhost, лимит редиректов, таймаут, лимит размера ответа) |
| NFR-08 | Безопасность | Экспортные файлы генерируются во временную директорию с немедленной отдачей; логирование всех экспортов (кто/что/когда) |
| NFR-09 | i18n | Все строки интерфейса — через i18n-ресурсы; локали ru-RU и en-US из коробки; формат чисел/дат по локали пользователя |
| NFR-10 | Доступность | WCAG 2.1 AA для UI фильтров/конфигураторов: клавиатурная навигация, aria-атрибуты, контрастность AUI |
| NFR-11 | Надёжность | Ошибки макроса не ломают страницу: graceful fallback в статичную таблицу с сообщением об ошибке |
| NFR-12 | Наблюдаемость | Структурные логи (ключевые события: SQL-запрос, экспорт, ошибка) с request-id; health-check DC (`HealthCheckModuleDescriptor`): доступность AO, кластерного кэша |
| NFR-13 | Апгрейд/откат | Установка/обновление/удаление без ручных SQL; при удалении — данные страниц сохраняются (макросы рендерятся как статичные таблицы-заглушки) |

## 9. Storage format и миграция со Stiltsoft (опционально, но рекомендуется)

- Наши макросы используют **собственное пространство имён**: `opentfc-table-filter`, `opentfc-chart`, `opentfc-pivot`, `opentfc-transformer`, `opentfc-spreadsheet`, `opentfc-spreadsheet-include`, `opentfc-attachment-table`, `opentfc-csv`, `opentfc-json`.
- Параметрическая схема повторяет проверенные semantics прототипа (имена параметров — camelCase, как в AC-подобных макросах), что упростит автоконвертацию.
- **Модуль миграции (C):** скрипт/REST-задача, которая по пространству находит макросы Stiltsoft (`table-filter`, `chart-from-table`, `pivot-table`, `table-transformer`, `table-spreadsheet`, `table-spreadsheet-include`, `attachment-table`) и переписывает storage format на наши имена с маппингом параметров. Спредшиты Stiltsoft: конвертация их вложений в XLSX → импорт через SP-07.

## 10. REST API (v1)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/rest/opentfc/1.0/source/{pageId}/{macroId}` | Данные источника (пагинация, серверный парс CSV/JSON/XLSX) |
| POST | `/rest/opentfc/1.0/transformer/{pageId}/{macroId}/query` | Выполнить SQL, вернуть результат (с лимитами) |
| GET/POST/DELETE | `/rest/opentfc/1.0/profile/{pageId}/{macroId}` | CRUD профилей фильтров текущего пользователя |
| POST | `/rest/opentfc/1.0/export/csv` | Экспорт текущего состояния таблицы (тело — модель), ответ — файл |
| GET | `/rest/opentfc/1.0/spreadsheet/{pageId}/{attachmentId}` | Загрузить модель спредшита |
| PUT | `/rest/opentfc/1.0/spreadsheet/{pageId}/{attachmentId}` | Сохранить (If-Match по версии вложения — оптимистичная блокировка) |
| GET | `/rest/opentfc/1.0/config` | Клиентская конфигурация (лимиты, локаль, whitelist-признаки) |
| POST | `/admin/rest/opentfc/1.0/migrate/stiltsoft` | Миграция пространства (admin-only) |

Все эндпоинты: права проверяются на сервере, XSRF на мутациях, rate-limit (админ-настройка).

## 11. Установка и развёртывание («до полной установки»)

### 11.1. Сборка
```
atlas-mvn package          → target/opentfc-x.y.z.jar (или .obr)
atlas-run / atlas-debug    → dev-инстанс Confluence для проверки
```
Артефакт: один JAR (все зависимости — shaded с relocation, кроме предоставляемых Confluence: AUI, AO, WRM). Контроль конфликтов классов обязателен (DuckDB и POI — в собственный classloader-пространство плагина).

### 11.2. Установка на прод
1. ⚙️ → **Manage apps** → **Upload app** → выбрать JAR.
2. Проверка: приложение в списке «User-installed», статус enabled, ошибки в `atlassian-confluence.log` отсутствуют.
3. Прогнать **Smoke-чеклист** (раздел 12.3) на тестовом пространстве.
4. При наличии Stiltsoft — сначала миграция контента (раздел 9), затем отключение/удаление Stiltsoft, затем контрольный smoke.
5. Откат: Uninstall (контент деградирует до статичных таблиц — проверено NFR-13).

### 11.3. Требования к поставке
- Исходный код (git-репозиторий, README с инструкцией сборки).
- JAR-артефакт релиза + changelog.
- Документация: администратора (установка, лимиты, whitelist, кластер) и пользователя (по каждому макросу, ru/en).
- CI: сборка на JDK 17, юнит- и интеграционные тесты (`atlas-integration-tests`), lint storage-format XML.

## 12. Тестирование и приёмка

### 12.1. Уровни
- **Юнит:** парсеры (CSV/JSON/типы колонок), SQL-препроцессор, маппинг параметров, i18n.
- **Интеграционные (Confluence test harness):** рендер каждого макроса, storage format round-trip, REST с правами/XSRF, AO-миграции, кластерные события (2 ноды, atlas-run-standalone ×2).
- **UI (Playwright):** сценарии фильтрации/диаграмм/пивота/спредшита на эталонных страницах.
- **Нагрузочное:** NFR-01…NFR-03 на эталонных данных.

### 12.2. Критерии приёмки (извлечение)
- Все **M**-требования раздела 7 реализованы и демонстрируются на приёмочном пространстве.
- Юнит-покрытие backend ≥ 70 %; интеграционные тесты зелёные на 8.5 LTS и актуальном 9.x LTS.
- Кластерный тест: правка спредшита на ноде A видима на ноде B ≤ 5 с; инвалидация источника CSV — ≤ 5 с на обеих нодах.
- Отсутствие критических уязвимостей сканером зависимостей (OWASP dependency-check: без High/Critical).

### 12.3. Smoke-чеклист (после установки, обязателен для «полной установки»)
1. Создать страницу: таблица 500 строк → обернуть Table Filter → фильтры/сортировка/totals/пагинация работают; сохранить профиль; экспорт CSV/XLSX.
2. Тот же фильтр поверх макроса Jira Issues (тестовый проект) — фильтруется.
3. Chart from Table: column + pie + Gantt на данных из таблицы; PNG-экспорт.
4. Pivot Table: группировка по 2 полям, агрегат SUM + % of column total.
5. Table Transformer: `SELECT T1.'Name', T2.Salary FROM T1 JOIN T2 ON T1.ID = T2.ID` — результат корректен; пресет Merge.
6. Table Spreadsheet: создать, ввести формулы (SUM, VLOOKUP, SUMIF), форматирование, сохранить, обновить страницу — данные на месте; экспорт XLSX и обратный импорт.
7. Spreadsheet Include на другой странице — отражает изменения исходника.
8. Attachment Table + фильтр по типу файла.
9. CSV Table из вложения (cp1251, `;`) — распарсен корректно.
10. Права: пользователь read-only видит фильтры, но не может сохранить спредшит; REST-мутация без XSRF отклоняется.
11. PDF-экспорт страницы со всеми макросами — статичные представления без ошибок.

## 14. Риски и ограничения

| Риск | Влияние | Митигация |
|---|---|---|
| Univer (OSS-core) не закроет все фичи прототипа (сложные диаграммы в листе, co-editing) | Среднее | Scope SP-04 минимальный; co-editing заменён мягкой блокировкой (SP-08); запасной путь — x-spreadsheet-функциональность руками на своей модели |
| DuckDB JDBC тяжёлый (~50 МБ, native libs) | Среднее | Шейдинг в изолированный пакет; ленивая инициализация движка только при наличии Transformer на странице |
| Поведение «обёртывания» чужих макросов нестабильно между версиями Confluence | Высокое | Интеграционные тесты на 2 LTS-линейках; белый список поддерживаемых макросов-источников + graceful fallback |
| Атлас-API меняется в 9.x (deprecations) | Среднее | Использовать стабильные API (Renderer/AttachmentService), избегать внутренних классов |
| Конкурентное редактирование спредшитов | Среднее | Оптимистичная блокировка по версии вложения (If-Match), UX для конфликта |
| AG Grid license путаница (Community/Enterprise) | Низкое | Юридический контроль: только community-пакет `ag-grid-community`, запрет enterprise-модулей; либо Tabulator |
